# Tech Stack

- You are building a React application.
- Use TypeScript.
- Use React Router. KEEP the routes in src/App.tsx
- Always put source code in the src folder.
- Put pages into src/pages/
- Put components into src/components/
- The main page (default page) is src/pages/Index.tsx
- UPDATE the main page to include the new components. OTHERWISE, the user can NOT see any components!
- ALWAYS try to use the shadcn/ui library.
- Tailwind CSS: always use Tailwind CSS for styling components. Utilize Tailwind classes extensively for layout, spacing, colors, and other design aspects.

Available packages and libraries:

- The lucide-react package is installed for icons.
- O `jspdf` está instalado para gerar PDFs (sempre por import dinâmico, para não pesar no bundle inicial).
- You ALREADY have ALL the shadcn/ui components and their dependencies installed. So you don't need to install them again.
- You have ALL the necessary Radix UI components installed.
- Use prebuilt components from the shadcn/ui library after importing them. Note that these files shouldn't be edited, so make new components if you need to change them.

# Backend (Supabase)

- Cliente: `src/lib/supabase.ts` (somente chave pública; nunca usar `service_role` no browser).
- Autenticação: `src/contexts/AuthContext.tsx` (`AuthProvider` envolve o app em `src/App.tsx`; consumir com `useAuth`). Rotas privadas devem usar `<ProtectedRoute>` de `src/components/ProtectedRoute.tsx`.
- Dados da família: `src/contexts/FamilyContext.tsx` (`useFamily`) carrega família, membros, convites, permissões e atividades e concentra todas as mutações (criar família, convidar, alterar papéis, salvar permissões).
- Fluxo de convite: link público `/convite/:token` (`src/pages/AcceptInvite.tsx`) valida o e-mail logado e cria a membership.
- Tipos das tabelas: `src/types/database.ts`.
- Documentação do banco: `docs/supabase-schema.sql` (script de referência já aplicado no projeto).
- Tabelas: `profiles`, `families`, `family_members`, `family_invitations`, `family_permissions`, `pregnancies`, `pregnancy_milestones`, `appointments`, `appointment_attachments`, `exams`, `exam_attachments`, `medications`, `medication_attachments`, `medication_doses`, `expenses`, `expense_attachments`, `notifications`, `activity_logs`.
- Gestação: `pregnancies` guarda DUM/data de referência, ciclo, DPP e observações (um registro ativo por família). Cálculos de semanas, DPP e marcos ficam em `src/lib/pregnancy.ts`; a tela é `/gestacao` (`src/pages/Pregnancy.tsx`). Escrita exige `family.edit`; leitura é liberada para membros ativos.
- Perfil do bebê: `baby_profiles` (nome, `birth_date`, `birth_time`, `birth_weight` em kg, `birth_height` e `head_circumference` em cm, maternidade, pediatra, `important_info`, `avatar_url`) — **um registro por família** (`family_id` único, sem linha duplicada). `avatar_url` guarda o **caminho** da foto no bucket privado `baby` (sempre via URL assinada). Leitura por membro ativo; escrita exige `family.edit`. **Regra do módulo**: sem `birth_date` cadastrada, `Rotina`, `Vacinas` e `Crescimento` ficam bloqueados no menu (`requiresBabyBirthDate` em `src/lib/nav.ts`) e nas telas (`BabyModuleGate`). O trigger `sync_family_baby_profile` espelha nome e data em `families.baby_name`/`baby_birth_date` para o resumo da home. Tela `/bebe/perfil` (`src/pages/BabyProfile.tsx`), helpers em `src/lib/baby.ts`.
- Marcos personalizados: `pregnancy_milestones` (título, `event_date`, descrição). Leitura por membro ativo; criação exige `records.create`; remoção pelo autor ou por `records.delete`. A linha do tempo mistura etapas padrão + marcos, sempre ordenada por data.
- Diário de cuidados (Rotina): `baby_logs` (`log_type` fixo — `fralda`, `mamadeira`, `amamentacao`, `sono`, `banho`, `medicamento`, `temperatura`, `evacuacao`, `outro` —, `logged_at` como instante, `details` JSONB com as variações de cada tipo e `notes`). Leitura por membro ativo; INSERT exige `records.create` e `user_id = auth.uid()` (quem registrou); DELETE pelo autor ou por `records.delete`. **Append-only**: não há update — para corrigir, remove e registra de novo. O formato de `details` por tipo está em `BabyLogDetails` (`src/types/database.ts`), rótulos/cores/sumários em `src/lib/babyLogs.ts` e o formulário em `src/components/BabyLogDialog.tsx`. A tela `/rotina` (`src/pages/Routine.tsx` → `src/components/RoutineDiary.tsx`) mostra "últimos acontecimentos", atalhos coloridos por tipo e os registros do dia; continua atrás do `BabyModuleGate` (exige `birth_date`).
- Fralda · Estoque: a troca de fralda pode baixar um produto do estoque (`baby_logs.inventory_item_id` + `stock_quantity`, sempre opcional). O trigger `apply_diaper_stock` registra a `saida_uso` em `inventory_movements` (o saldo é subtraído por `apply_inventory_movement`) e o trigger `restore_diaper_stock` devolve a quantidade como `ajuste_manual` quando o registro do diário é removido. Só vale para `log_type = 'fralda'`; o select **Produto Utilizado** lista todos os `inventory_items` (os sem saldo ficam bloqueados), a quantidade padrão é 1 e o formulário mostra o saldo restante.
- Vacinas: `vaccines` (nome, dose, `expected_date`, `applied_date`, local, lote, profissional, `proof_path` no bucket privado `vaccines`, observações; exige ao menos uma das datas). Leitura por membro ativo; criação `records.create` + `created_by = auth.uid()`, edição `records.edit`, remoção pelo autor ou `records.delete`. Status derivado em `src/lib/vaccines.ts` — aplicada (verde), atrasada quando `expected_date` passou sem aplicação (vermelho) e prevista. Tela `/vacinas` (`src/pages/Vaccines.tsx` → `src/components/VaccineTimeline.tsx`, formulário em `VaccineForm.tsx`).
- Crescimento: `growth_records` (`weight` em kg `numeric(5,2)`, `height` e `head_circumference` em cm `numeric(5,1)`, `measurement_date`; pelo menos uma medida). Mesmas permissões das vacinas. Gráfico de linhas com `recharts` em `src/components/GrowthChart.tsx` (peso à esquerda, cm à direita, séries alternáveis) e helpers em `src/lib/growth.ts`. Tela `/crescimento` (`src/pages/Growth.tsx`, formulário em `GrowthForm.tsx`). `numeric` pode voltar como texto: o `FamilyContext` normaliza com `Number()`.
- Datas: usar sempre `date-fns` (`parseISO`/`format`/`differenceInCalendarDays`) em `src/lib/family.ts`, `src/lib/pregnancy.ts` e `src/lib/medications.ts`. Datas são dias de calendário `"AAAA-MM-DD"`; nunca converter para UTC (`toISOString`) para evitar deslocamento de fuso. Horários de medicamentos são `time` no banco (`HH:MM:SS`) e `HH:MM` na interface; o instante de confirmação (`confirmed_at`) é `timestamptz`.
- Consultas: `appointments` (médico, especialidade, clínica, endereço, `scheduled_at`, motivo, observações, recomendações, status) + `appointment_attachments`. `scheduled_at` é instante (`timestamptz`): converter o valor do input `datetime-local` com `new Date(valor).toISOString()` e exibir com `date-fns` (hora local). Leitura por membro ativo; escrita exige `calendar.manage`. Tela `/consultas` (`src/pages/Appointments.tsx`), helpers em `src/lib/appointments.ts`.
- Exames: `exams` (nome, datas solicitada/agendada/realizada, médico solicitante, laboratório, resultado, observações) + `exam_attachments`. Leitura por membro ativo; criação exige `records.create`, edição `records.edit`, remoção pelo autor ou `records.delete`. Tela `/exames` (`src/pages/Exams.tsx`); a listagem agrupa exames de mesmo nome para comparação (`src/lib/exams.ts`).
- Vitaminas e medicamentos: `medications` (nome, `dosage` + `dosage_unit`, `times` como `time[]`, `frequency` `daily`/`every_other_day`/`weekly`/`as_needed`, início/término, médico) + `medication_attachments` e bucket privado `prescriptions`. `medication_doses` é o histórico de adesão: uma linha por dose confirmada (`dose_date`, `dose_time`, status `taken`/`late`/`missed`, `confirmed_by`, `confirmed_at`), única por (medicamento, dia, horário) e com check que exige confirmação. O checklist do dia é sempre derivado das regras do cadastro (`buildDayChecklist` e `adherenceStats` em `src/lib/medications.ts`), nunca pré-gerado. Escrita exige `records.create` (edição `records.edit`, remoção pelo autor ou `records.delete`); confirmar dose grava sempre o usuário logado. Tela `/medicamentos` (`src/pages/Medications.tsx`). O app não recomenda, ajusta nem prescreve nada — apenas registra o que a família cadastra.
- Central de notificações internas: `notifications` (`kind` `appointment`/`exam`/`medication`/`pending`, `dedupe_key` único por família, `due_at`, `read_at`/`read_by`). As linhas são geradas **no servidor** por `generate_family_notifications(p_family_id)` (security definer, exige `is_family_member`), chamada com `supabase.rpc` em cada carregamento do `FamilyContext`: ela faz upsert do que está válido e apaga o que deixou de valer (dose registrada, consulta atualizada). O cliente só lê e marca como lida (update direto no próprio aviso); não existe push nem e-mail. Regras: consultas agendadas/remarcadas nos próximos 7 dias, exames com data agendada nos próximos 7 dias, doses de hoje sem registro (conforme `frequency`/`times`) e pendências (exame realizado sem resultado, exame agendado vencido, consulta vencida ainda agendada). Rótulos em `src/lib/notifications.ts`; UI em `src/components/NotificationCenter.tsx` (sino no `AppShell`, desktop e mobile).
- Financeiro: `expenses` (data, produto/serviço, `category` fixa — `roupas`, `higiene`, `moveis`, `quarto`, `alimentacao`, `saude`, `consultas_exames`, `transporte`, `brinquedos`, `outros` —, `amount_cents` inteiro, `paid_by`, `store`, descrição/observações) + `expense_attachments` e bucket privado `receipts`. Valores são **centavos inteiros** (`parseAmountToCents`/`formatCents` em `src/lib/expenses.ts`), nunca float. Leitura por membro ativo; escrita exige `records.create`, edição `records.edit`, remoção pelo autor ou `records.delete`. Tela `/financeiro` (`src/pages/Expenses.tsx`) com indicadores (total gasto, categorias, últimos 4 meses, últimas compras), busca e filtros por data/categoria. Helpers: `categoryTotals`, `monthlyTotals`, `monthTotalsFor`, `latestExpenses`, `filterExpenses`.
- Enxoval: `layette_items` (nome, `category` fixa — `roupas`, `berco`, `banho`, `alimentacao`, `passeio`, `quarto`, `brinquedos`, `outros` —, `desired_quantity`, `purchased_quantity` padrão 0, `estimated_price_cents`/`actual_price_cents` em centavos **por unidade**, `store_link` (http/https), `responsible`, `status` `desejado`/`pesquisando`/`comprado`/`recebido`/`presenteado`, observações). Leitura por membro ativo; criação exige `records.create`, edição `records.edit`, remoção pelo autor ou `records.delete`. Tela `/enxoval` (`src/pages/Layette.tsx`) com progresso (peças compradas/desejadas), estimado × gasto, filtros por categoria/status/busca e cards com **Registrar compra**, edição e exclusão. O item só aparece como **Concluído** quando `purchased_quantity >= desired_quantity` (derivado, nunca um status gravado); abaixo disso o card mostra o status de origem e "faltam N peças". Helpers em `src/lib/layette.ts` (`layetteTotals`, `filterLayette`, `sortLayette`, `layetteStatusMeta`, `layetteDisplayStatus`, `layetteRemainingUnits`); moeda reutiliza `formatCents`/`parseAmountToCents` de `src/lib/expenses.ts`.
- Presentes: `gifts` (`product_name`, `date_received`, `giver_name`, `quantity` = unidades recebidas, `description`, `photo_path` único no bucket privado `gifts`, `notes`, `layette_item_id` opcional, `cost_cents` opcional = custo que a família teve). Leitura por membro ativo; criação exige `records.create`, edição `records.edit`, remoção pelo autor ou `records.delete`. **Regras de negócio no banco**: (a) o trigger `apply_gift_layette` **soma** `quantity` na `purchased_quantity` do item vinculado (delta correto ao editar a quantidade, trocar o vínculo e ao excluir o presente) — nunca força o item inteiro como concluído; o select do formulário só oferece itens com `purchased_quantity < desired_quantity` (`linkableLayetteItems` em `src/lib/gifts.ts`). (b) o trigger `sync_gift_expense` cria/atualiza/remove **uma** despesa por presente quando `cost_cents` está preenchido (categoria do item do enxoval via `layette_expense_category`, ou `outros`; `expenses.gift_id` com `on delete cascade`); sem valor, nada entra no Financeiro. Tela `/presentes` (`src/pages/Gifts.tsx`) com cards (quem deu, data, custo e foto por URL assinada via `StorageImage`) e formulário com foto opcional, checkbox **Gerou custo para a família?** + campo **Valor (R$)**.
- Estoque: `inventory_items` (`product_name`, `brand`, `size`, `current_quantity` e `minimum_stock` em `numeric(10,2)`, `unit` fixa — `un`, `pacote`, `caixa`, `par`, `frasco`, `rolo`, `ml`, `l`, `g`, `kg`). Leitura por membro ativo; criação exige `records.create`, edição `records.edit`, remoção pelo autor ou `records.delete`. O alerta **Estoque baixo** é derivado (`current_quantity <= minimum_stock`, `isLowStock` em `src/lib/inventory.ts`) — nunca armazenado. `numeric` pode voltar como texto do Data API: o `FamilyContext` normaliza com `Number()`; a UI usa `formatQuantity`/`parseQuantity`/`formatStock`. Tela `/estoque` (`src/pages/Inventory.tsx`) com cards, faixa de alerta e `updated_at` relativo.
- Movimentações de estoque: `inventory_movements` (`inventory_item_id`, `movement_type` `entrada_compra`/`entrada_presente`/`saida_uso`/`ajuste_manual`, `quantity`, `occurred_at` como instante, `user_id` e observações). **Append-only**: leitura por membro ativo e INSERT com `records.create` + `user_id = auth.uid()`; não há UPDATE/DELETE de propósito (apagar um movimento desalinharia o saldo). O saldo é ajustado **no banco** pelo trigger `apply_inventory_movement` (security definer): entradas somam, saídas subtraem e `ajuste_manual` define o valor; saída maior que o saldo gera erro, e `updated_at` do produto é atualizado pelo trigger do item. O cliente nunca escreve `current_quantity` diretamente. UI em `src/components/InventoryHistoryDialog.tsx` (clicar no card de `/estoque` abre detalhes + histórico + formulário rápido), metadados em `src/lib/inventory.ts` (`inventoryMovementMeta`, `movementQuantityLabel`, `formatMovementDate`).
- Central de Documentos: `documents` (nome, `category` fixa — `exames`, `vacinas`, `gestacao`, `identidade`, `financeiro`, `outros` —, `date`, `description`, `file_path` no bucket privado `documents`). Leitura por membro ativo; criação exige `records.create` + `created_by = auth.uid()`, edição `records.edit`, remoção pelo autor ou `records.delete`. O upload acontece antes da linha (caminho `<family_id>/<document_id>/<uuid>-<arquivo>`); se a gravação falhar o arquivo é removido. Visualização e download só por URL assinada (`createSignedFileUrl`/`downloadStoredFile`). Tela `/documentos` (`src/pages/Documents.tsx`, formulário em `DocumentForm.tsx`) com busca pelo nome, filtro por categoria, miniatura para imagens e ícone por tipo (`src/lib/documents.ts`).
- Memórias: `memories` (`title`, `date`, `description`, `category` fixa — `primeiro_ultrassom`, `nascimento`, `primeiro_banho`, `primeiro_sorriso`, `primeira_palavra`, `primeiros_passos`, `primeira_comida`, `primeira_viagem`, `aniversario`, `outros` —, `media_path` opcional — foto ou vídeo no bucket privado `memories` — e `is_favorite`). Leitura por membro ativo; criação exige `records.create` + `created_by = auth.uid()`, edição `records.edit`, remoção pelo autor ou `records.delete`. O upload acontece antes da linha (`<family_id>/<memory_id>/<uuid>-<arquivo>`); se a gravação falhar o arquivo é removido, e ao substituir/remover a mídia o arquivo antigo sai do storage. **Favoritar não exige `records.edit`**: a RPC `toggle_memory_favorite(p_memory_id)` (security definer) só alterna `is_favorite` e valida `is_family_member`. Tela `/memorias` (`src/pages/Memories.tsx`) com linha do tempo vertical (mais recente primeiro, agrupada por mês), filtro **Todas / Favoritas** e cards em `MemoryCard.tsx`; formulário em `MemoryForm.tsx`, mídia por URL assinada em `MemoryMedia.tsx`, helpers em `src/lib/memories.ts` (`sortMemories`, `filterMemories`, `groupMemoriesByMonth`, `memoryMediaKind`, `validateMemoryMedia`).
- Relatórios: `/relatorios` (`src/pages/Reports.tsx`) com período (início/fim + presets "Este mês", "Mês passado", "Últimos 30 dias") e resumo de saúde, financeiro e rotina do bebê. Os dados do período vêm de `useReportData` (`src/hooks/useReportData.ts`), que consulta `appointments`, `exams`, `medications`, `expenses`, `baby_logs` e `vaccines` direto do Supabase com a sessão do usuário — o RLS é a autorização (o `.eq("family_id")` é redundante de propósito) e o diário não sofre o limite de 300 linhas do `FamilyContext`; consultas, despesas e diário são filtrados no banco pelo intervalo. Agregação pura em `src/lib/reports.ts` (`buildReportSummary`, `expensesInPeriod`, `formatPeriod`, `reportPresets`, `reportCategoryColors`). Exportações em `src/lib/reportExports.ts`: CSV detalhado das despesas do período (separador `;` + BOM para o Excel) e PDF do resumo com `jspdf` (`downloadReportPdf`). Gráfico de rosca dos gastos por categoria em `src/components/ExpenseCategoryChart.tsx` (recharts).
- Anexos: helpers genéricos em `src/lib/attachments.ts` (`validateAttachment`, `safeStorageFileName`, `createSignedFileUrl`, `downloadStoredFile`, `AttachmentPicker`). Buckets privados `appointments`, `exams`, `prescriptions`, `receipts`, `gifts`, `baby`, `vaccines`, `documents` e `memories` (10 MB para imagens/PDF; o bucket `memories` aceita vídeos até 50 MB), caminho `<family_id>/<registro_id>/<arquivo>`; as policies de `storage.objects` validam o primeiro segmento com `is_family_member`/`has_family_permission`. Download somente via URL assinada.
- Integração Enxoval · Financeiro · Presentes · Estoque: (1) **compra explícita** — o card de `/enxoval` tem o botão **Registrar compra**, que abre `LayettePurchaseDialog` (quantidade comprada, valor total, quem pagou, data) e chama a RPC `purchase_layette_item`: as unidades são **somadas** em `purchased_quantity` (nunca substituídas), `actual_price_cents` vira a média ponderada do total já pago por unidade e a despesa entra em `expenses` (`layette_item_id` + categoria via `layette_expense_category`); exige `records.edit` e `records.create`. Mudar o status no formulário **não** pede valor nem lança gasto. (2) **presente** — vincular ao enxoval (`layette_item_id`) soma `quantity` no item e só cria despesa se `cost_cents` estiver marcado. (3) **estoque por presente** — marcar “Adicionar ao estoque” grava `inventory_item_id` + `stock_quantity` no `gifts` e o trigger `apply_gift_stock` cria a movimentação `entrada_presente` (o saldo é somado por `apply_inventory_movement`). Espelho da categoria em TS: `layetteExpenseCategory` em `src/lib/layette.ts`. Regra das quantidades: **Concluído** é sempre derivado (`purchased_quantity >= desired_quantity`, `layetteItemComplete`/`layetteDisplayStatus` em `src/lib/layette.ts`) e nunca é forçado no registro.
- Integração Saúde · Financeiro: `appointments` e `exams` têm `is_private` + `cost_cents`; `medications` tem `cost_cents`. Nas telas, o switch **Particular** com valor (R$) e o valor opcional do medicamento alimentam os triggers `sync_appointment_expense` / `sync_exam_expense` (categoria `consultas_exames`, nome/descrição com o médico ou exame, data e local) e `sync_medication_expense` (categoria `saude`). Sem valor — ou com Particular desmarcado — **nenhuma** despesa é criada e a derivada é removida. A despesa guarda `appointment_id`/`exam_id`/`medication_id` (`on delete cascade`), é atualizada em vez de duplicada, e a função interna `upsert_health_expense` não é executável pelo cliente (revoke de `anon`/`authenticated`).
- Autorização é sempre por RLS: o isolamento deriva de `family_members` (funções `current_user_family_ids()`, `is_family_member()`, `has_family_permission()`). Toda tabela nova precisa de RLS habilitado, policies por operação e grants do Data API.
- Nunca inserir dados fictícios no banco do usuário.

# Design

- Idioma da interface: português do Brasil.
- Mobile-first, com barra de navegação inferior no mobile (5 destinos + “Mais”, que abre um `Sheet` com exames e ajustes da família) e sidebar no desktop (`src/components/AppShell.tsx`). Itens de menu com `requiresBabyBirthDate` mostram cadeado e ficam esmaecidos enquanto o perfil do bebê não tiver data de nascimento.
- Paleta em variáveis CSS (`src/globals.css`): pêssego coral (primary), lavanda, menta, creme e os apoios `sky`, `rose`, `clay` e `sand` (usados nos tipos do diário de rotina). Tipografia: Fraunces (títulos) e Plus Jakarta Sans (texto).
